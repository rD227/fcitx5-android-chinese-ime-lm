# 拼音纠错：方法与当前实现

## 调研结论

中文输入法需要联合考虑「打字错误的可能性」「词典/用户词频」「整句是否自然」。
可采用带键盘位置权重的编辑距离，处理替换、插入、删除和相邻颠倒，
再用束搜索保留多条解码路径，由语言模型评分。错误更多不等于纠得更好：
若只按汉字是否通顺排序，可能将原本正确的专有名词改成另一个常见句子。

参考原始资料：

- [Suzuki & Gao, 2012](https://aclanthology.org/D12-1056/)：将在线拼写纠错与音译输入联合解码。
- [KNPTC, 2018](https://arxiv.org/abs/1805.00741)：将从实际打字数据得到的字母转换知识结合到神经模型中。
- [Zheng 等，ACL 2011](https://aclanthology.org/P11-2085/)：分析真实拼音输入中的漏按、多按、替换和交换。邻键误按与发音混淆是不同原因，例如 `g/f` 属于邻键，`a/e` 还涉及拼音发音混淆，不能全部按键盘距离处理。
- [chinese-ime-lm 的纠错探针](https://github.com/metasequoiaime/chinese-ime-lm/blob/main/eval/probes/README.md)：现有模型接收汉字候选，不接收拼音；假想候选探针不能代替真实引擎评测。
- [本项目锁定版本的 Rime corrector](https://github.com/rime/librime/blob/de4700e9f6b75b109910613df907965e3cbe0567/src/rime/dict/corrector.cc)：实际使用邻键替换；编辑距离分支在该版本中被禁用。

## 本次修改

1. 全拼可启用 `chinese_ime_lm/enable_transposition: true`。在每个可能的音节前缀上枚举一次相邻交换，交给真实 Rime prism 验证，不包含词语或整串输入的替换表。
2. 早期实现每音节只允许一次邻键替换或一次相邻交换。Rime 对不同距离使用同一惩罚；后续两步键盘扩展及代价修正见下文。
3. 首选为自动组句时，从当前读取的九项候选中查找同音前缀，在已有词条的完整边界处替换，再保留原句剩余词条。必须保持同一音节 ID 路径、语言、输入跨度和学习信息。由模型在完整句子之间比较。
4. 原有候选和尾部仍可选择；精确词典首选、预测补全和前缀候选的保护继续保留。原重排器最多比较九个完整候选，不读取其他应用内容，也不记录用户输入。

这一步没有重新训练权重，也没有把 `haoyourenma` 等输入写进运行时代码。
`tests/*.tsv` 中的词语只用于测试。

## 0.1.4：更积极的候选生成

版本配置为基础名称 `0.1.4`、基础版本码 12，arm64 的 APK versionCode 为 `122`。主程序兼容基线仍为 `0.1.3 / 112`，本次没有更新原生依赖或模型权重。

- 原生同排表已有 `n/m`、`y/u`、`i/o`。`enable_keyboard_neighbors` 补充错位 QWERTY 的跨排近键；额外搜索仅用于原方案无法接受的片段。这样可处理 `huaj → huan`，也保护有效的 `ming`，避免凭键位把“明天见”改成“今天见”。该开关默认跟随 `enable_transposition`。
- `chinese_ime_lm/aggressive` 默认开启。新增 `sentence-decoder.h` 从实际 ScriptTranslator 的系统词典和用户词典中提取词条，在选定的全拼音节路径上重新组合不同分词，保留 4 条中间路径、最多 32 条完整组合。没有词语替换表。
- 使用真实 DictEntry、语言、音节跨度和原 syllabifier，选词上屏与学习对应同一个候选。相同文字的不同分词保留词典分数较好的路径。
- 在一次组合中缓存稳定的拼音前缀；新查询必须重绑 syllabifier，提交、取消、删词、已选前文或用户词典启用状态改变时失效。
- 新组合放在原重排器选定的首选之后。试验中同时放宽词典保护、拼音路径和首选决策，22 条诊断的首选从 20 条降至 14 条，因此这套直接接管首选的方案没有采用。上游也说明当前神经直接解码尚不及原引擎，见 [项目说明](https://github.com/metasequoiaime/chinese-ime-lm)。

真机副本对照：原有 22 条仍为 20 条首选正确；`tests/aggressive.tsv` 的 19 条从 14 条变为 17 条，未观察到原本正确的首选退化。这仍是手选诊断，不是整体准确率。

新增首选修复包括：

| 输入 | 原首选 | 新首选 |
| --- | --- | --- |
| `woxihuajni` | 我学会安静 | 我喜欢你 |
| `siexieni` | 蹀躞你 | 谢谢你 |
| `wozaixuexizhojgwen` | 我在学习中甲骨文 | 我在学习中文 |

`wozaidadianzi` 可生成“我再打点字”，最终 4 路束搜索的一次测试中是第 20 项；其实际组件、跨度、选择和上屏通过原生测试。首选仍为“我在大电子”，所以该例只解决了完整候选生成，尚未解决首选判断；没有外部上下文时也不能保证“在/再”的意图。

## 两步键盘搜索与开关

按错键使用错位 QWERTY 的邻接图，覆盖同排和跨排，不逐条硬编码拼音或词语。
`nri → nei` 按用户意图表示 `e` 误按成 `r`；原始规则的书写方向不影响这个测试目标。
键盘几何是近似布局，不是根据手机实际触点或个人使用记录训练得到的概率。

| 类型 | 例子 | 代价 |
| --- | --- | ---: |
| 一处邻键误按 | `nri → nei`、`je → ke`、`frn → fen` | 1 |
| 同音节两处邻键误按 | `mro → mei`、`cue → xie`、`shwbg → sheng` | 2 |
| 一处跨两个键位 | `vi → xi`（经过 c） | 2 |
| 一次相邻交换 | `suhang → shuang`、`tain → tian` | 1 |

搜索预算为每音节两步，通过真实 prism 字典树剪枝。附加邻键搜索只扩展方案尚不接受的拼写；两步搜索必须保留至少一个原字母。完全替换短音节会通过简拼路径引入无关整词，不能靠移除词典首选保护来掩盖这个问题。

锁定的 Rime `Syllabifier` 虽接收 `Correction.distance`，却把所有纠错赋予同一个 `log(0.01)` 权重。`correction-distance.cpp` 使用链接器 `--wrap` 调用原图构建，再将增强纠错边的可信度恢复为每步代价之和；不修改节点和索引地址，保持真实跨度和学习信息。一步为 `log(0.01)`，两步为 `2 × log(0.01)`。仅增强 corrector 使用此适配，原生模式保持原行为。内部头文件新增两个只读非虚访问器，不改变对象布局。

这是与固定 Rime/Android libc++/ABI 绑定的适配，不代表任意预编译库均兼容。移植要求见 [AGENT.md](../../../AGENT.md) 和 [来源记录](UPSTREAM.md)。

### 这一批规则的验证

在独立 RimeIce 副本中移除个人手写纠错派生规则，只启用引擎和插件配置，以免把已有手写规则误算为代码效果。

- 原先 50 组误按目标覆盖 46 组；修正后 50/50。补入 `je → ke` 后为 **51/51**。
- 这里检查的是完整音节 ID 可达及其进入词典/组句前的实际图权重，不代表对应汉字一定首选。`cue` 同时可达 `xue` 和 `xie`，仍有真实歧义。
- 在同一无手写规则副本的原有 41 条有效整句诊断中，首选命中由 36 条增至 37 条，1 条改善、0 条已正确首选退化。另加入 `haijeyi` 和正常对照 `haikeyi`，两者都首选“还可以”。这些均是手选诊断，不能当作总体准确率。
- 四组交换目标通过；其中上游方案已能接受的别名不计为新增纠错收益。
- 原生、单步、两处误按、较远键位、交换、全关共六组配置中的 **24 项启停断言通过**。另有滤镜关闭测试确认重排和组句停止，避免只测试“配置能被读取”。

`zuiwanle` 的实际纠错发生在 `zui → zuo` 音节，实测首选“做完了”；把整串 `zuowanle` 当作单音节派生来源不可靠。`ranh` 在基础方案中已可通过简拼得到“然后”，不能算新增修复。
`v` 单键当作 `b` 声母属于缩写/按键约定；此全拼纠错未覆盖该类缩写，仍由方案设置处理。

复核命令（只能传入独立副本，命令会部署方案）：

```sh
rime-neural-smoke --check-spellings <用户副本> <共享目录> rime_ice <keyboard-spellings.tsv>
rime-neural-smoke --check-spellings <用户副本> <共享目录> rime_ice <transposed-spellings.tsv>
```

TSV 的 `reject` 类型要求目标不可达，用于检查关闭开关后的行为。批量反复修改测试副本时须确保对应编译方案确实重新生成；该版本 Rime 的源文件时间戳精确到秒，秒内多次写回可能被当作未改变。

### 交换搜索优化及正常切分

原循环对不同长度重复交换同一对字母。现在每个位置只交换一次，用一次字典树前缀查询验证所有可能的音节长度，同时要求匹配长度包含被交换的两个字母。六字母输入由最多 15 次前缀查询减为 5 次，未改变可搜索的交换集合；单元测试同时验证 `'` 分隔符不可跨越。

`suhang` 即使可以正常切成 `su'hang`，也会检查 `shuang` 的交换路径；不是必须“完全无法切分”才检查。真实 prism/图测试确认整音节 `shuang` 可达，至于“爽/双”和“苏杭”的候选顺序仍取决于词典、切分和排序。显式输入 `su'hang` 会固定这个边界。

每个功能的 `.custom.yaml` 开关、默认值及关闭示例见 [README](README.md#每项功能都可独立关闭)。未带别名的滤镜默认配置区已经从通用的 `filter` 映射为文档中的 `chinese_ime_lm`；明确指定的自定义别名仍使用自己的配置区。新增原生代码和资源编译通过，本次没有启动 Gradle 或安装新版 APK。

## 未解决

- `shuurufa → 输入法`：通用多按/漏按的候选生成尚未实现。词典缩写能偶尔处理漏字，但不等于通用删除/插入纠错。
- `zhongwne → 中文`：正确读法已进入候选，但首选仍可能是另一个词典词。需要把真实纠错路径的证据传给排序器，不能简单删除所有词典保护。
- 相邻颠倒以外的任意换位、跨音节错位、长句多个错误以及双拼尚未验证。
- 当前组合搜索固定在原有全拼音节路径上，没有同时搜索任意拼音切分或多个纠错路径。

后续重训应使用真实引擎录制的候选和明确授权的错拼数据，训练/验证按原句分组切分，
同时报告正常输入被误改的比例、候选覆盖率与按键延迟。若改为直接学习拼音到汉字，
需增加字母词表和相应输入结构，不能把现有汉字语言模型当作已支持这种任务。
