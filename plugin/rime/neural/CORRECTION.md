# 拼音纠错：方法与当前实现

## 调研结论

中文输入法需要联合考虑「打字错误的可能性」「词典/用户词频」「整句是否自然」。
可采用带键盘位置权重的编辑距离，处理替换、插入、删除和相邻颠倒，
再用束搜索保留多条解码路径，由语言模型评分。错误更多不等于纠得更好：
若只按汉字是否通顺排序，可能将原本正确的专有名词改成另一个常见句子。

参考原始资料：

- [Suzuki & Gao, 2012](https://aclanthology.org/D12-1056/)：将在线拼写纠错与音译输入联合解码。
- [KNPTC, 2018](https://arxiv.org/abs/1805.00741)：将从实际打字数据得到的字母转换知识结合到神经模型中。
- [Zheng 等，ACL 2011](https://aclanthology.org/P11-2085/)：分析真实拼音输入中的漏按、多按、替换和交换。邻键误按与发音混淆是不同原因，例如 `g/f` 属于邻键，`a/e` 还涉及拼音发音混淆，不能全部按键盘距离处理。
- [chinese-ime-lm 的纠错探针](https://github.com/metasequoiaime/chinese-ime-lm/blob/main/eval/probes/README.md)：现有模型接收汉字候选，不接收拼音；假想候选探针不能代替真实引擎评测。
- [本项目锁定版本的 Rime corrector](https://github.com/rime/librime/blob/de4700e9f6b75b109910613df907965e3cbe0567/src/rime/dict/corrector.cc)：实际使用邻键替换；编辑距离分支在该版本中被禁用。

## 本次修改

1. 全拼可启用 `chinese_ime_lm/enable_transposition: true`。在每个可能的音节前缀上枚举一次相邻交换，交给真实 Rime prism 验证，不包含词语或整串输入的替换表。
2. 早期实现每音节只允许一次邻键替换或一次相邻交换。Rime 对不同距离使用同一惩罚；后续两步键盘扩展及代价修正见下文。
3. 首选为自动组句时，从当前读取的九项候选中查找同音前缀，在已有词条的完整边界处替换，再保留原句剩余词条。必须保持同一音节 ID 路径、语言、输入跨度和学习信息。由模型在完整句子之间比较。
4. 原有候选和尾部仍可选择；精确词典首选、预测补全和前缀候选的保护继续保留。原重排器最多比较九个完整候选，不读取其他应用内容，也不记录用户输入。

这一步没有重新训练权重，也没有把 `haoyourenma` 等输入写进运行时代码。
`tests/*.tsv` 中的词语只用于测试。

## 两步键盘搜索与开关

按错键使用错位 QWERTY 的邻接图，覆盖同排和跨排，不逐条硬编码拼音或词语。
`nri → nei` 按用户意图表示 `e` 误按成 `r`；原始规则的书写方向不影响这个测试目标。
键盘几何是近似布局，不是根据手机实际触点或个人使用记录训练得到的概率。

| 类型 | 例子 | 代价 |
| --- | --- | ---: |
| 一处邻键误按 | `nri → nei`、`je → ke`、`frn → fen` | 1 |
| 同音节两处邻键误按 | `mro → mei`、`cue → xie`、`shwbg → sheng` | 2 |
| 一处跨两个键位 | `vi → xi`（经过 c） | 2 |
| 一次相邻交换 | `suhang → shuang`、`tain → tian` | 1 |

搜索预算为每音节两步，通过真实 prism 字典树剪枝。附加邻键搜索只扩展方案尚不接受的拼写；两步搜索必须保留至少一个原字母。完全替换短音节会通过简拼路径引入无关整词，不能靠移除词典首选保护来掩盖这个问题。

锁定的 Rime `Syllabifier` 虽接收 `Correction.distance`，却把所有纠错赋予同一个 `log(0.01)` 权重。`correction-distance.cpp` 使用链接器 `--wrap` 调用原图构建，再将增强纠错边的可信度恢复为每步代价之和；不修改节点和索引地址，保持真实跨度和学习信息。一步为 `log(0.01)`，两步为 `2 × log(0.01)`。仅增强 corrector 使用此适配，原生模式保持原行为。内部头文件新增两个只读非虚访问器，不改变对象布局。

这是与固定 Rime/Android libc++/ABI 绑定的适配，不代表任意预编译库均兼容。移植要求见 [AGENT.md](../../../AGENT.md) 和 [来源记录](UPSTREAM.md)。

### 交换搜索优化及正常切分

原循环对不同长度重复交换同一对字母。现在每个位置只交换一次，用一次字典树前缀查询验证所有可能的音节长度，同时要求匹配长度包含被交换的两个字母。六字母输入由最多 15 次前缀查询减为 5 次，未改变可搜索的交换集合；单元测试同时验证 `'` 分隔符不可跨越。

`suhang` 即使可以正常切成 `su'hang`，也会检查 `shuang` 的交换路径；不是必须“完全无法切分”才检查。真实 prism/图测试确认整音节 `shuang` 可达，至于“爽/双”和“苏杭”的候选顺序仍取决于词典、切分和排序。显式输入 `su'hang` 会固定这个边界。

每个功能的 `.custom.yaml` 开关、默认值及关闭示例见 [README](README.md#每项功能都可独立关闭)。未带别名的滤镜默认配置区已经从通用的 `filter` 映射为文档中的 `chinese_ime_lm`；明确指定的自定义别名仍使用自己的配置区。新增原生代码和资源编译通过，本次没有启动 Gradle 或安装新版 APK。

## 合法全拼遮住混合简拼：`shuo` 与 `s'huo`

这类问题有两种合法解释：`shuo` 是“说”，也能按 `s + huo` 解读，其中 `s` 是“生”的简拼，得到“生活”。它不属于邻键误按；`xian → 西安` 等完整音节切分歧义也应单列。

核对 LineageOS 测试机的用户 custom 和实际编译方案，简拼规则仍然存在。用当前配置副本和不含个人手写纠错规则的副本分别验证，都得到 `shuo → 说`、`s'huo → 生活`。因此这次没有通过改写个人配置处理。

根因有两处：锁定版本的 Rime 图构建在完整正常拼写到达末尾时，会剪掉较弱的简拼路径；原滤镜又只对自动组句 `sentence` 工作，完整字典词 `phrase` 直接返回。单纯提高键盘替换预算或让模型重排原候选，不能找回被剪掉的词。

新分支 `mixed-abbreviations.h` 从当前方案真实 prism 中寻找“简拼前缀 + 完整音节后缀”，再直接查询当前系统词典和启用的用户词典。只接受覆盖全部输入的真实双音节词，不预测长词、不重新组合单字句子、不枚举任意漏字。每次最多补 8 个去重候选，保留原首选及剩余候选。

每个词保留真实 `DictEntry`、语言和来源，独立的 syllabifier 保存原始输入边界。例如“生活”的音节 ID 是 `sheng + huo`，原始输入跨度是 `[0, 1, 4]`，不是把四字母输入伪装成完整 `shenghuo`。非零分段起点也有跨度测试。

### 开关与边界

```yaml
patch:
  chinese_ime_lm/enable_mixed_abbreviations: false
```

默认 `true`。它是独立的混合简拼候选补充，不依赖 `translator/enable_correction`、`aggressive` 或模型是否加载；不会接管首选，当前不使用模型重排这批附加词。关闭或未启用该词典分支时，显式输入 `s'huo` 仍可让原方案按此边界解析。

目前只覆盖单个完整音节与“简拼前缀 + 完整音节”之间的冲突，没有开放任意双向简拼或长句所有切分。后续若允许上下文提升此类候选，须联合拼音证据验证，不能因为某个词更通顺就替代正常全拼。相关研究：[统计拼音输入中的切分与打字模型](https://www.microsoft.com/en-us/research/publication/a-new-statistical-approach-to-chinese-pinyin-input/)、[PinyinGPT 对简拼歧义的分析](https://aclanthology.org/2022.acl-long.133/)。也通过 agy 的 Gemini 4 Argon 独立讨论了这一分类和例子，最终效果以真实词典和设备测试为准。

本次只使用指定的 LineageOS 设备与独立数据副本，没有操作 PLK110、修改日常用户配置或安装新版 APK。

## 分次输入的词典首选与上下文

分次上屏“还在”，再输入 `paidui`，旧版对完整词典词直接返回，也没有向这条路径传递已提交前文。独立测试副本中的用户词典曾将“派对”排在“排队”前，旧策略不能结合前文调整这个顺序。

新分支仅允许有实际前文时、相同语言/音节 ID/原始跨度的完整 `phrase` 或 `user_phrase` 参与模型比较。结合前文得分更高还不够：相对首选的优势须大于无前文时的优势，才可提升。真实 4M 权重中，“生日”后仍单纯偏爱常见的“排队”，但其优势比无前文时减小；此条件保留“派对”。没有用词语替换表，也没有改模型权重。
